# 새 프로젝트 적용 가이드

이 보일러플레이트는 문서·코드·결정·검증 근거를 같은 저장소에서 관리하기 위한 출발점이다. 제품 도메인, 앱 수, 구현 언어, 패키지 관리자, 배포 서비스는 적용 프로젝트에서 결정한다.

## 최초 적용

1. `docs/product/overview.md`에 실제 제품 방향·사용자·범위·비목표를 채운다. 승인되지 않은 아이디어는 현재 제품으로 쓰지 않는다.
2. 루트 `CLAUDE.md`에 프로젝트의 통합 브랜치, 코드·테스트·빌드 명령, 배포 경계, 필요한 추가 규칙을 기록한다. `AGENTS.md`는 이 파일을 참조한다. 별도 통합 브랜치가 없다면 저장소 기본 브랜치를 기준으로 작업한다.
3. `CAP-000-template.md`를 복제해 실제 기능 영역을 정의하고, `PRD-000-template.md`를 복제해 하나 이상의 CAP에 연결한다. 파일명과 frontmatter ID를 함께 바꾸고 날짜·제목·책임자·범위를 채운다. `000`은 템플릿 전용이다.
4. 필요한 ADR·DDR·API만 추가한다. 번호는 이미 병합된 문서와 열린 PR을 확인해 배정하고 중복을 피한다. 저장소에 없는 제안 번호를 관계 필드에 넣지 않는다.
5. 기술 구조를 결정하면 실제 구현·테스트 경로를 추가하고 `docs/README.md`의 예시 트리와 `docs/architecture/current.md`를 갱신한다. 빈 `apps/`나 특정 앱 이름을 관성적으로 만들지 않는다.
6. 디자인을 구현하면 `docs/design/system/README.md`에 현재 승인 기준선과 실제 토큰·컴포넌트 경로를 연결한다. 과거 승인본과 현재 실행 코드를 구분한다.
7. [문서 검사](README.md)를 실행하고 생성된 다섯 인덱스와 원문을 함께 커밋한다. `.github/workflows/docs.yml`은 GitHub-hosted Linux에서 문서 검사만 수행하며 제품 배포·DB·시크릿 설정을 전제하지 않는다.

Node.js는 문서 도구의 실행 요건이다. 제품이 Node.js 프로젝트여야 하는 것은 아니며, 기존 빌드 시스템에는 같은 검사 명령을 추가할 수 있다.

## 보조 기록의 위치

| 기록 | 위치 | 정본과 연결하는 방법 |
| --- | --- | --- |
| 요청 원문·인터뷰·초안 정제 | [requirements](../requirements/README.md) | PRD 승격 전에는 승인 스펙으로 취급하지 않는다. |
| 실행 방법·순서·검토 | [plans](../plans/README.md) | PRD·WORK를 참조하고 작업 상태를 복제하지 않는다. |
| 구현 과정·핸드오프 | [implementation](../implementation/README.md) | 변경 경로·결정·검증 근거를 연결한다. |
| 검증 실행 결과 | [test-reports](../test-reports/README.md) | PRD Validation·Work Items에서 보고서를 참조한다. |

기록이 필요할 때 파일을 추가한다. 안내 파일만 있는 디렉터리는 아직 실제 작업이 없는 초기 상태다.

## 유지보수

- 파일·앱을 추가·이동·폐기하면 현재 구조 지도와 관련 계약을 함께 정합한다. 역사 결정·Change Log는 그 시점의 기록으로 보존한다.
- 상세 요구사항과 작업 상태는 PRD에서만 바꾼다. 수집 문서·실행 계획·외부 도구에서 작업을 진행했어도 완료 근거는 PRD에 연결한다.
- 생성 표를 수동 편집하지 않는다. 새 문서가 등록됐는데 인덱스에서 안 보이거나 상태가 다르면 원문부터 검사한다.
- 추가 AI 규칙이 필요한 범위에만 `CLAUDE.md`·`AGENTS.md` 쌍을 둔다. 공통 규칙을 복제하지 않는다.
- 기존 프로젝트에 적용할 때는 먼저 기존 문서·파서·작업 보드가 소비하는 계약을 조사한다. 파일 이동·ID 재배정·대량 상태 변경을 단순 템플릿 복사로 수행하지 않는다.
